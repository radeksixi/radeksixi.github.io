Sixi-ASI Engine 1.0.0-rc3: what two days under a talking agent found, and the engine's sources

Radek Brus · 17 November 2026 · download, measured results and check scripts

The second release candidate spent two days under an agent that talks and listens: about 4,500 chat requests and 2,600 speech requests, none of them failed. It still brought back a list. A sampled answer that began with a stray character, calls that took up to four times longer than they had to, and a spoken Polish "nie" that came back as "Yeah.". The third candidate fixes that list, every number below was measured on its archive, and the engine's sources are in the repository again.

The same prompt, first greedy, then sampled

An agent that does not like its own answer asks again with a temperature. Up to rc2, when the first answer to a prompt had been written at temperature 0, a sampled request for the same prompt began with a stray character nine times in ten: a *, a +, a digit. With a prompt that demands JSON the answer was that character alone. The engine keeps what it has computed for a prompt, and in this one case it kept too little to sample from.

No gate of mine had ever asked the same prompt twice with two temperatures, so the gate has a new check now: five questions with one certain answer, greedy and then sampled with six seeds, and the other way round. rc2 gives 20 right of 45, rc3 gives 45. It is in the archive as scripts/sampling_check.py.

An agent with roles pays for its prompts

A turn of that agent is three calls, each with its own system prompt of one to two thousand tokens and an answer of twenty. Such a call is almost all prompt, and reading a prompt does not get faster with more requests at once. What decides its cost is how much of the prompt the server still has, and rc2 had none of it: three roles pushed each other's prompts out, even inside one session.

rc3 keeps the end of every long system prompt on its own, and every later call with that system prompt starts from there, whichever conversation it belongs to.

86% of the prompt tokens are not read again (rc2: 0 to 7%), and the server answers 1.2 such calls a second in total instead of 0.35. There is one rule to follow on the agent's side: the system message has to be identical from call to call. Whatever changes per turn belongs in the user message. usage.prompt_cached_tokens in every answer says whether it worked.

"Nie" is not "Yeah."

The speech service recognises with Parakeet, which has no input for the language: it decides from the audio. A word of one syllable is too little to decide from, and it writes an English word. Of 80 clips of Polish speakers saying "nie", it heard 2 right and wrote "Yeah." for 37. For an agent that asks a yes-or-no question, that is the worst word to get wrong.

Silence around the clip does not help, and a second recogniser told the language is better but slow and inventive (it wrote "Dzięki za oglądanie" for some clips). What helps is context in the right language: with language=pl in the request, the service hears a short clip together with a phrase in Polish spoken by its own voice, and takes the phrase off the text again. The same for German, French and Italian.

The number I care about most is the middle one. A wrong word looks like an answer; an empty text only makes the agent ask again. Wrong words fall from every second clip to one in fourteen for Polish, at 0.2 to 0.35 seconds a clip on CPU cores. Where even that is too many, certain=1 returns a text only when the clip was heard the same way twice (180 right, 12 wrong, 108 empty on the Polish clips).

A caution about these clips: they are single words cut out of sentences that people read aloud (the Multilingual Spoken Words Corpus, CC-BY 4.0), so they are harder than an answer said on its own, and two thirds is a floor, not the rate you will see. Words said by the service's own voices come back 30 of 30 in Polish with the better of its two voices. The check is in the archive (scripts/speech_short_check.py) and takes a folder of your own recordings.

Smaller things

  • Logs. After two days the engine's log had 2.2 million lines, 2.1 million of them debug lines of the library underneath. They are gone, and the speech service's log no longer holds any recognised or spoken text: timings and character counts only.
  • The same audio twice. A voice draws random noise, so one sentence is different audio every time. "deterministic": true in a synthesis request gives the same audio for the same text, which is what a test needs.
  • Numbers in a small picture. The model sees a picture at one row per 32 by 32 pixels. Of fifteen 480-pixel pictures of a six-digit number it reads 5 at the picture's own 225 rows and 14 with --image-min-tokens 1024. llama.cpp's own server reads the same 5 and 14 at the same settings; the guide now says when to raise the rows.

The engine's sources

From rc1 the engine went out as an archive only. With rc3 its sources are in the repository again, under Apache-2.0: the server and its API, speculative decoding, parallel streams, structured answers, images, request priority, the prompt states described above, the sixi and sixi-speech commands, the tests and the measurement scripts.

cmake -B build -DCMAKE_BUILD_TYPE=Release -DSIXI_VERSION_SUFFIX=-rc3
cmake --build build -j
ctest --test-dir build --output-on-failure

The programs load their backend at run time, and that part stays binary for now: the archive's library is llama.cpp v1.0.0 with this engine's kernel and drafter changes. A server built from the repository and run with that library writes the same tokens at the same speed as the released one (60 of 60 prompts of the speed test, 54.9 against 54.7 tok/s).

How the numbers were taken

  • On the released archive, unpacked fresh, not on a development build. Its programs and library are the files the full gate ran on in the morning; only texts and Python scripts changed after it.
  • Greedy decoding and identical prompts unless a row says otherwise. Other work used the machine's CPU cores that day, so wherever rc3 is compared with rc2 the two ran in turn.
  • That mattered once. rc3 keeps eight prompt states where rc2 kept four, and two alternating runs made it look as if that cost one percent of single-stream speed. Ten runs later it was the spread of a shared machine: 54.7 tok/s with 4 states, 55.1 with 8, 54.9 with 16 in the same hour. I had already written the one percent down, and took it out again.
  • The higher totals for many requests at once come from prompt loading, not from decoding: the test repeats five prompts and rc3 still has all of them. A stream decodes as fast as in rc2.

rc3 decodes like rc2 and is a better thing to build an agent on: a second, sampled try works, a role's long prompt is read once, and a one-word answer is heard in the language it was said in. Full tables: docs/RESULTS.md; a talking agent on one Thor: docs/VOICE-AGENT.md.
