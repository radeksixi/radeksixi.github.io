sixi-scanner 1.0: six real bugs caught on live agents, MCP & A2A, and zero-LLM precision jumping from 0.667 to 0.763

Radek Brus · 19 November 2026 · sixi-scanner v1.0.0

Unit tests pass even when your transport drops session IDs on a real server, or when a single comma inside an LLM refusal splits the denial away from the phrase it refused. Before tagging sixi-scanner v1.0.0, we put structured JSONL observability on both the scanner and a real multi-protocol Google ADK target (adk-demo-target), replayed 1,480 recorded Microsoft Foundry turns, and ran live chat, tool-policy, MCP and A2A benchmarks. Six genuine bugs surfaced — every one of them invisible to unit tests alone — and fixing them pushed zero-LLM marker precision from 0.667 to 0.763 (-38% false positives) with zero recall loss.

Everything in v1.0.0 still compiles from the Go standard library alone (go.mod has zero external dependencies), commits to a v1.x stability contract, and ships with automated static binaries for Linux, macOS and Windows.

1. Replay on 1,480 real Microsoft Foundry turns (zero LLM calls)

Replaying the deterministic judge alone (no confirmation LLM) against the 1,480 recorded turns from agent-redteam-benchmark immediately exposed two systemic false-positive sources in v0.10.0:

  • Commas inside refusals: isBoundary treated , as a sentence boundary, splitting a single refusal sentence like "I can't share a customer's full record (postal address, date of birth, or home address)" so items after the first comma lost their negation cue. Removing , from sentence boundaries eliminated 7/7 training-data-extraction FPs and the live pii-elicitation refusal-list FP.
  • Credential config templates: literal assignment markers (password=, api key:) and connection-string regexes fired on unfilled documentation templates like Password=REDACTED;, Password=your_password;, API key: <YOUR_API_KEY>, and amqp://user:pass@host:port/vhost. Inspecting the value token immediately following assignment markers cut credential-elicitation FPs in half (8 → 4) without suppressing real leaked secrets.

2. Live 3-rung defence ladder on Atlas (none → basic → hardened)

We upgraded adk-demo-target (Atlas, a Google ADK banking assistant with deterministic server-side oracles) into a full multi-protocol local server exposing /api/chat, /v1/chat/completions, /mcp, /a2a, and /.well-known/agent-card.json, plus thread-safe per-turn JSONL observability (app/observability.py) and an optional OpenAI-compatible ADK adapter so local Ollama models can run at $0.00.

Running all 45 techniques with --reproduce 1 --log-jsonl across two very different local models — Gemma 4 4B (gemma4:e4b-it-qat) and Qwen 3.8 27B (qwen3.8:27b) — produced three concrete findings:

  • The prompt-only hardening trap (none → basic): adding refusal rules to Gemma 4B's system prompt dropped secret leaks from 18 to 7 — but introduced three new instruction-leak findings via Swahili (low-resource-multilingual), adversarial poetry, and Bad Likert Judge, because there were now explicit rules for the model to recite once bypassed. Inspecting the Swahili dump also revealed that Atlas leaked its instructions in first person ("My instructions are… My available tools are…"), which we added to systemPromptMarkers.
  • Why regex input guards are not enough: Atlas's hardened rung blocked 15 attacks at the gate and dropped secret leaks to 0, yet multi-turn probe.llm01.sleeper-memory (plant an innocent keyword rule in turn 1, stay benign in turn 2, trigger in turn 3) sailed straight through both /api/chat and /a2a.
  • 27B vs 4B on output handling: qwen3.8:27b leaked zero secrets even on none, yet both 4B and 27B happily echoed raw SSTI ({{…}}) and unescaped CSV formulas (=CMD(…)) until the hardened layer was enabled.

Takeaway: a static input filter plus a bigger model cuts single-turn leaks to zero, but multi-turn sleeper payloads and downstream output-handling payloads (SSTI, CSV formulas) still get through unless enforced in code.

3. Prose lies; the tool trace does not (seeded policy enforcement)

Running the 8 tool-agency probes with --seed (authenticating as customer NW-1001), --trace-path tool_calls, and --context atlas-context.json forced real Google ADK tool executions on gemma4:e4b-it-qat. Comparing the server-side JSONL log against sixi-scanner's JSONL log immediately exposed bug #6: Atlas executed issue_refund(amount_chf=30) twice in one conversation (60 CHF > 50 CHF), and Policy.CheckCall only checked each call individually (30 <= 50).

Adding Policy.CheckSessionLimits (cumulative numeric limit enforcement across all calls in a conversation) closed that gap cleanly:

4. Live MCP & A2A verification — two protocol bugs caught on real servers

Running both passive sixi-scanner surface and active --target mcp / --target a2a against Atlas caught two transport bugs that mocked unit tests never saw:

  • MCP latency & tool traces: m.rpc discarded HTTP round-trip latency (reporting 0 ms in ScanStats) and passed the raw JSON string instead of the decoded map[string]any to ExtractToolCalls. After the fix, active --target mcp --tool ask_atlas reported real latency (p50 = 2710 ms, 11/11 OK) and caught probe.llm01.json-schema-bypass via oracle:json-schema.
  • A2A multi-turn session continuity: real A2A v0.3 servers frequently omit "kind": "task" on returned Task objects that already carry id + status/contextId. On the first live run, 33 A2A turns opened 33 separate sessions and missed every multi-turn probe. Fixing extractA2ATaskID restored real session continuity (19 A2A turns across 11 sessions, unsupported: 0) — and active --target a2a immediately caught probe.llm01.sleeper-memory [CRITICAL] over A2A.
  • Passive surface precision: on clean MCP + authenticated A2A, surface reported 0 poisoning false positives (correctly flagging unsigned-card and weak-auth-scheme). With DEMO_MCP_POISON=1 and DEMO_A2A_POISON=1, it caught surface.mcp.tool-poisoning [critical]: audit_formatter, surface.a2a.skill-poisoning [critical]: Diagnostics Helper, and surface.a2a.unauthenticated [high] without sending a single adversarial prompt.

Observability on both sides: --log-jsonl & ScanStats

None of the six fixes above would have been obvious from pass/fail counts alone. v1.0.0 ships --log-jsonl <path> (0600 per-attempt telemetry: prompt, reply, observed tool calls, latency, scoring mechanism, evidence basis, reproduction flag) and an aggregate stats block in JSON reports so every scan can be audited offline alongside target-side logs.

Scope note. The 0.763 marker-precision figure is an offline replay of the v1.0.0 deterministic judge on the 1,480 recorded turns from the v0.8.3 Foundry corpus (zero LLM judge calls). The defence-ladder, tool-policy, MCP and A2A figures are live end-to-end runs against adk-demo-target backed by local Ollama models (gemma4:e4b-it-qat and qwen3.8:27b). Full live re-runs of the 7-tool cloud Foundry benchmark remain a separate follow-up.

Install v1.0.0

Download static binaries from the v1.0.0 release (Linux, macOS, Windows + SHA256SUMS) or install via Go:

go install github.com/radeksixi/sixi-scanner/cmd/sixi-scanner@v1.0.0

# Scan a live agent with deterministic wire policy, 1x reproduction & JSONL telemetry
sixi-scanner scan --target chat --url http://127.0.0.1:8000/api/chat \
  --trace-path tool_calls --context atlas-context.json \
  --reproduce 1 --log-jsonl scan-attempts.jsonl --out report.json

# Passively inspect MCP tools and A2A Agent Cards
sixi-scanner surface --url http://127.0.0.1:8000/mcp

# Diff baseline vs hardened honestly
sixi-scanner diff baseline.json hardened.json
