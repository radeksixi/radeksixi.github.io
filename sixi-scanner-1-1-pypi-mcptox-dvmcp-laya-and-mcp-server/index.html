sixi-scanner 1.1 on PyPI & Official MCP Registry: four third-party benchmarks, 80.6% MCPTox recall, live rug-pull detection, and native laya-as-judge

Radek Brus · 23 November 2026 · PyPI v1.1.0 · GitHub Release · MCP Registry (io.github.radeksixi/sixi-scanner)

sixi-scanner v1.1.0 (Apache-2.0, still Go standard library only — 0 external dependencies) is now live on PyPI (uvx sixi-scanner / pip install sixi-scanner across Linux, macOS & Windows), the Official MCP Registry (io.github.radeksixi/sixi-scanner via sixi-scanner mcp-serve), and GitHub Actions (action.yml). Before shipping a single line of new code, I ran v1.0.0 against four independent third-party benchmarks — MCPTox (AAAI 2026), DVMCP, DVAA, and JailbreakBench — to see where it actually broke outside my own test harnesses.

1. Three real failures that third-party benchmarks exposed in v1.0.0

Testing a scanner only against your own demo agents gives you comfortable numbers and blind spots. Running v1.0.0 unmodified against four external suites immediately surfaced three concrete gaps:

  1. Modern FastMCP Streamable HTTP (2025-03-26) returned HTTP 406 on all 15/15 DVMCP challenges. v1.0.0 sent Accept: application/json without text/event-stream, did not persist Mcp-Session-Id, and did not send notifications/initialized or unwrap SSE data: frames.
  2. Natural-language tool poisoning missed 62% of MCPTox (AAAI 2026). Against 1,348 real poisoned MCP tools, v1.0.0 caught only 38.06% (513/1,348) — and just 3.71% on the stealth pure_tool.json subset that avoids XML tags like <IMPORTANT> and instead uses phrases like "ignore the previous instructions", "do not inform the user", or mandatory prerequisite hijacks.
  3. Diagnostic tool-error echoes caused false positives on strict agents. When an MCP tool or agent returned a validation error quoting our probe text (e.g. Error: unexpected value "..."), the substring marker scorer could match markers reflected from our own input — producing 22 false positives on DVMCP Challenge 2 and 22 on DVAA ToolBot.

2. Before vs. after across all four third-party benchmarks

Fixing those three root causes — without weakening refusal handling or adding external dependencies — produced clean, measurable gains across every external dataset:

3. Detecting both manifest and delayed-output MCP Rug Pulls (--rug-pull)

Single-shot MCP inspection misses rug-pull servers that behave cleanly during initial discovery and turn hostile after a trust-building period. In real MCP benchmarks there are two distinct patterns: a server that mutates its tools/list schema mid-session, and a server like DVMCP Challenge 4 whose tools/list never changes — instead, get_weather returns clean data on calls 1–3 and starts appending hidden <IMPORTANT> exfiltration instructions on call #4.

sixi-scanner surface --rug-pull handles both deterministically: it SHA-256 hashes every tool's (name, description, inputSchema) across repeated snapshots and sends benign read-only calls to safe non-mutating tools between snapshots, scanning each tool output against baseline round #1. Verified live against unmodified DVMCP Challenge 4:

$ sixi-scanner surface --url http://127.0.0.1:9004/mcp
# exit 0 — 0 findings (clean initial manifest)

$ sixi-scanner surface --url http://127.0.0.1:9004/mcp --rug-pull
# exit 1 — [CRITICAL] surface.mcp.rug-pull:
# MCP tool output mutated to inject instructions after 4 benign calls (rug pull): get_weather

4. Eleven zero-dependency connectors + native laya-as-judge confirmation

Rather than adding vendor SDKs, v1.1.0 speaks every major cloud and local AI protocol over Go's net/http:

  • 11 connectors: openai (OpenAI, NVIDIA NIM, NeMo Guardrails, Sixi-ASI, vLLM, Ollama), responses (OpenAI Responses API & Microsoft AI Foundry /v1/responses with native previous_response_id), azure (Azure OpenAI / Foundry api-key + api-version), gemini (Google Gemini generateContent / Vertex AI + functionCall), anthropic (Anthropic Messages /v1/messages + tool_use), mcp (JSON-RPC 2.0 + Streamable HTTP 2025-03-26), a2a, json, chat, webform, and echo.
  • --stateful multi-turn on cloud APIs: maintains isolated client-side conversation history per session so multi-turn probes (sleeper-memory, refund-cap-split, payload-relay) run cleanly on openai, azure, gemini, and anthropic.
  • Native laya-as-judge confirmation: pointing --confirm-url at /v1/judge, /v1/judged-decision, /v1/decisions, or /v1/systemone automatically sends typed noul + choice criteria and honours orthogonal ActionGate block verdicts without needing --confirm-model.
  • Prefix-cache-friendly LLM judges: OpenAI-compatible confirmation calls now place the invariant auditor contract and agent policy in role: "system" and only the candidate exchange in role: "user", raising KV prefix-cache hit rate to 92.38% on local Sixi-ASI / vLLM servers.

5. One command via PyPI, GitHub Actions, or your AI IDE (MCP Server)

Because Python wheels wrap the pre-compiled static Go binary for all five platforms, teams no longer need a Go toolchain to run sixi-scanner or attach it to Claude Desktop / Cursor / Windsurf:

# Run instantly via uvx or pip (Linux x86_64/arm64, macOS x86_64/arm64, Windows x86_64)
uvx sixi-scanner surface --url https://your-agent.example --rug-pull
pip install sixi-scanner

# Or wire directly into an MCP-capable IDE (Official MCP Registry: io.github.radeksixi/sixi-scanner)
{
  "mcpServers": {
    "sixi-scanner": {
      "command": "uvx",
      "args": ["sixi-scanner", "mcp-serve"]
    }
  }
}

In CI, the composite action.yml downloads the SHA-256-verified static binary for your runner and exports SARIF 2.1.0 straight to GitHub Code Scanning.
